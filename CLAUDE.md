## Commands

```bash
cargo test                                  # Run all tests (integration + doctests)
cargo test --test ranting                   # Integration tests only (single target "ranting" = tests/ranting/main.rs)
cargo test --test ranting singular_they     # Single test module/test by name filter
cargo test --doc                            # Run doctests only
cargo test --features debug                 # Show compile-time placeholder transforms
cargo clippy --fix
cargo fmt
```

This repo is not a cargo workspace — `ranting`, `ranting_core`, `ranting_derive`, `ranting_i18n`
and `ranting_es` each have their own `Cargo.toml`/`Cargo.lock` — so the commands above, run at the
repo root, never compile or test `ranting_i18n`/`ranting_es` (or any future sibling crate
directory). Before trusting a green gate, also run `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo test`
inside each sibling crate directory, e.g. `cargo test --manifest-path ranting_i18n/Cargo.toml`.
`scripts/overnight_loop.sh`'s pre-flight check and its per-task gate (ROADMAP.md Phase 6 item 13)
already do this — its `gate_dirs`/`run_gate` helpers iterate every directory with its own
`Cargo.toml`, so a broken `ranting_i18n` (or a new sibling crate added later) fails the gate the
same as a broken `ranting`.

## Architecture: Three Library Crates + Two Downstream Falsifier Crates

The three crates below are the library. `ranting_i18n/` (crate name `ranting-i18n`, v1.3,
ROADMAP.md Phase 6 item 10) and `ranting_es/` (crate name `ranting-es`, Phase 6 item 23) are two
more directories but *not* part of it: each is a downstream consumer that depends on `ranting`
alone, exactly as an ecosystem fork would, and exists to falsify the claim that the public API
gives a non-English implementation enough signal. Nothing in
`ranting`/`ranting_core`/`ranting_derive` depends on either of them, and neither may ever gain a
`ranting_core` or `ranting_derive` dependency — the moment one needs it, that is the finding.

The two falsifiers were chosen to exercise different, complementary gaps rather than duplicate
each other. `ranting_i18n` implements German and found that German attributive adjectives are
prenominal (`der kleine Hund`) while `ranting`'s `!`/`!!` degree slot is post-noun only, so German
structurally *cannot* reach `inflect_adjective_custom` in a grammatically correct sentence — only
demonstrate the agreement mechanism in isolation. `ranting_es` implements Spanish specifically
*because* Spanish attributive adjectives are post-nominal (`el gato negro`, `la casa negra`),
exactly where the `!` slot renders, so it exercises `inflect_adjective_custom` with genuinely
correct output rather than a position mismatch. Each crate's `README.md` is the authoritative,
numbered list of what its language cannot reach through the public API, each pinned by a
`hole_N_*` test in its own `tests/holes.rs` that asserts what the crate *actually* renders (the
ROADMAP cross-references each hole from the item it belongs to). German records eight holes, of which three (2, 3, 4) are open, four (1, 5, 6, 7) are closed, and one (8, word order) is recorded as a permanent boundary rather than an unclosed gap;
Spanish's lexicon reproduces exactly one of them — preposition/article fusion (`ranting_i18n`
hole 7, restated in `ranting_es/README.md` for Spanish's own contraction pair, `de`+`el`→`del`
and `a`+`el`→`al`) — and documents the rest of German's holes as not applicable to Spanish's
grammar (no dative case, no adjective declension class, no zero-length indefinite plural article).

`ranting_gaps/` (crate name `ranting-gaps`, binary `ranting-gaps`, ROADMAP.md Phase 7 item 9) is
a third non-library sibling and is **not** a falsifier — read its dependency list before treating
it as precedent. It is a development tool that reads arbitrary English text and reports what
`ranting` cannot inflect, ranked by corpus frequency, into a generated `failures/` tree. Because
its job is to inspect `ranting` from outside rather than to prove the public API sufficient, it
depends on `ranting_core` as well as `ranting` — deliberately, using `ranting_core::ph_ext::parse`
as the authoritative oracle for the closed pre-noun vocabulary rather than restating that word
list (the hand-kept-duplication failure mode this file already records for
`PH_START`/`SENTENCE_TRIGGER_CHARS`). That dependency does **not** relax the falsifier contract on
`ranting_i18n`/`ranting_es`, which remains absolute. `failures/` at the repo root is its committed
output, regenerated by rerunning the tool — never hand-edited.

This repo is not a cargo workspace, so each of `ranting_i18n` and `ranting_es` has its own
`Cargo.lock` and its own `cargo fmt`/`clippy`/`test` runs, like `ranting_core` and
`ranting_derive`. `scripts/overnight_loop.sh`'s `gate_dirs` helper discovers every sibling crate
automatically by globbing for a `Cargo.toml`, so a future third falsifier (or any other sibling
directory) is gated the same way without editing the script.

**`ranting`** (main lib): Exports `Ranting` trait, `Noun` struct, `say!()` macro.  
**`ranting_derive`** (proc-macro): Implements `say!()`, `ack!()`, `nay!()`, `ask!()` macros. `ranting_impl.rs`'s `ranting_q` is the derive macro's core codegen entrypoint (builds the generated `Ranting` impl from the parsed `#[ranting(...)]` attributes); `str_lit.rs` wraps `syn::LitStr` for span-preserving compile-error substrings.  
**`ranting_core`** (plain rlib, v1.2): Internal-only shared grammar engine both of the above depend on as an ordinary path dependency — the `serde`/`serde_derive` pattern, where a proc-macro crate and its companion runtime crate both depend on a shared library crate rather than one crate generating a copy of the other's source at build time. Nothing in `ranting_core` is part of `ranting`'s public semver surface, even where `ranting` re-exports an item from it.

**What moved into `ranting_core`** (previously three separate build.rs-copy-into-`OUT_DIR` mechanisms, now one crate with no codegen-copying at all):
- `ranting_core::grammar` — the placeholder grammar (`PH_START`, `PH_EXT`), `SubjectPronoun` (+ `is_subject`/`is_subjective_plural`/`is_first_person_subject`), and the still-unused `Article`/`DemonstrativePronoun` enums (kept as documented dead code — see DONE.md Phase 4 item 1's implementation notes for why they weren't wired up or dropped). Formerly `src/language/english_shared.rs` (repo root), copied into `ranting_derive`'s `OUT_DIR` at build time and required to compile under two different `strum` major versions simultaneously (`ranting`'s 0.27 and `ranting_derive`'s 0.24) because it was included verbatim into both crates. That constraint is gone: `ranting_core` depends on a single `strum` version (0.27), and `ranting_derive` gets it transitively (the root `ranting` crate still declares `strum`/`strum_macros` directly in its own `Cargo.toml`) — `ranting_derive`'s own `Cargo.toml` no longer lists `strum`/`strum_macros` at all.
- `ranting_core::verb_conjugate` — `to_past`/`to_continuous`/`to_future`/`to_past_participle`, plus the generated `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` tables (from `data/irregular_verbs.txt`, via `ranting_core/build.rs` — the only place the *verb* tables are generated, though not the only build script in the repo: `build.rs` at the root generates the irregular-plural table into `ranting`'s own `OUT_DIR`, and `ranting_derive/build.rs` generates the irregular-adjective table into its own; `ranting`'s own `detect_tense` in `src/language/verb.rs` reads `ranting_core::verb_conjugate::IRREGULAR_PAST` instead of generating its own copy, and `ranting_derive` reads the same module for compile-time `say!()` literal baking).

**Also in `ranting_core`, added by Phase 4 items 3 and 6** (new modules, not part of the three-mechanism extraction above — together over 1200 lines, the majority of `ranting_core`):
- `ranting_core::placeholder` — the typed `PlaceholderSpec`/`CaseKind`/`PostSpec`/`ArticleKind`/`TenseMarker` types that replaced the old `caps: [&str; 5]` array and `~TENSE~`/`~DEGREE~` string sentinels at the macro↔runtime seam (Phase 4 item 3). `ranting_derive`'s `handle_param` bakes a `PlaceholderSpec` struct literal at compile time; `ranting`'s `handle_placeholder`/`handle_placeholder_with_context` (the module is re-exported via `pub use ranting_core::placeholder;`) consume it at runtime.
- `ranting_core::ph_ext` — a hand-written recursive-descent parser (`ph_ext::parse`) for the placeholder-internals grammar, replacing what the `PH_EXT` regex used to match (Phase 4 item 6). `ranting_derive`'s `parse_str_params` calls `ph_ext::parse` directly now; `PH_EXT` (in `grammar.rs`) is kept only as an `#[allow(dead_code)]` differential-fuzz reference oracle for `ph_ext`'s own test suite, not used at compile/runtime anymore.

**What stayed put, and why**: `src/language/plurals.rs`'s `get_plural`/`get_singular`/`apply_case` (joined 2026-08-14 by `regular_plural`/`compound_plural` — see the regular-pluralization bullet under "Non-obvious behaviors") used to be hand-duplicated in `ranting_derive/src/language/plurals.rs` too, but that copy was never called from anywhere in `ranting_derive` — noun pluralization happens at `Ranting::inflect()` runtime in `ranting`, never baked at compile time by the derive macro, so there was no call site to wire it into. Rather than carry permanently-dead code (and the `IRREGULAR_PLURALS`-table build.rs codegen that fed it) forever, the `ranting_derive` copy was deleted outright (2026-08-13, alongside fixing `ranting_derive`'s standalone `cargo clippy -D warnings` — see DONE.md Phase 4 item 6's follow-up note). The single remaining copy in `src/language/plurals.rs` is live: `english::inflect_noun_irregular`, which backs `Ranting::inflect()`'s irregular-noun path, delegates to it directly, so `Noun::inflect()` (and derive-generated `inflect()` impls) look up `data/irregular_plurals.txt` and preserve the original word's case pattern (all-caps/title-case/lowercase) via `apply_case`. `ranting_derive/src/language/adjective.rs` (comparative/superlative degree tables) is a different case and stayed in `ranting_derive` — it's genuinely used there for compile-time `!`/`!!` degree-marker baking, and `ranting` has no runtime use for it, so it was never one of the three shared-copy mechanisms Phase 4 item 1 replaced. See `docs/architecture-review-2026-08-13.md` for the pre-extraction history of the plurals drift, and DONE.md Phase 4 item 1's implementation notes for the full reasoning.

**Deleted**: both crates' build.rs copy-into-`OUT_DIR` steps for the code above, `ranting_derive/data/english_shared_source.rs`, `ranting_derive/data/verb_conjugate_source.rs`, and `ranting_derive/data/irregular_verbs.txt` (the packaged-build symlink fallbacks for the old copy mechanisms — `ranting_core` has its own `data/irregular_verbs.txt` → `../../data/irregular_verbs.txt` symlink now, for its own build.rs). `ranting_derive/Cargo.toml` no longer depends on `strum`/`strum_macros` at all — the dual-strum-version compilation constraint the "Key constraint" paragraph used to describe no longer exists, because the code that constraint applied to now compiles exactly once, in `ranting_core`.

**Macro flow**: Derive crate parses placeholders at compile-time, generates `format!()` calls. Runtime: `handle_placeholder()` applies final inflections via `Ranting` trait. `say_with!()` (v1.1) takes a `NarrationContext` as its first argument and calls `handle_placeholder_with_context()` instead — placeholders with tense markers (`<`,`=`,`>`,`<=`,`%`,`<%`) bake the *uninflected base verb* rather than a compile-time-conjugated form, so the marker can be overridden at runtime by `context.tense`. `say!()`'s codegen and output are untouched by this — it still bakes fully-conjugated literals and calls the original `handle_placeholder()`.

**`heed!()` input parsing** (v1.1): `heed!(template, input)` is the inverse direction of `say!()`'s placeholder syntax, but a deliberately smaller grammar — literal words plus `{name}`/`{name...}`/`{$name}` captures only, no article/verb/pronoun-case markers (see `docs/superpowers/specs/2026-08-12-input-parsing-feasibility.md` for why full grammatical inversion isn't attempted). `ranting_derive/src/heed.rs` compiles the template into an anchored regex at compile time; `ranting::HeedMatcher` (`src/heed.rs`) owns the actual `regex::Regex` (compiled once, cached via `OnceLock`) so generated code never references `regex::` types directly — this is why `ranting_derive`'s regex 1.6.0 and `ranting`'s regex 1.11 never need to match versions.

**`#[derive(Heed)]`** (v1.3, ROADMAP.md Phase 3 item 8's v2): struct-level sugar over `heed!()`, not a separate matching engine — `ranting_derive/src/heed_derive.rs::derive_heed` calls the same `heed::compile_heed_template` used by the `heed!()` macro, then generates `impl StructName { pub fn heed(input: &str) -> Option<Self> }`. `#[heed(template = "...")]` on the struct declares the template; every capture must have a same-named field and vice versa (a one-to-one mapping — a stale field or an unmapped capture is a compile error, not a silently-ignored gap), and each field's type is checked against its capture kind (`String` for `{name}`/`{name...}`, `u64` for `{$name}`). Only structs (named fields, or a unit struct for a zero-capture template) are supported — no enums. Field declaration order doesn't need to match template capture order; the derive maps by name. Sharing the compiler also means it inherits the whitespace-only word-boundary restriction verbatim — see the item-9 bullet in "Non-obvious behaviors" below.

## Non-obvious behaviors

- **Named arguments work** — `say!("{=x}", x)` (positional) and `say!("{=x}", x = val)` (named) both work today; see `tests/ranting/argument_edge_cases.rs`.
- **A template may write its own language's article keyword (2026-08-14, `docs/superpowers/specs/2026-08-14-language-modularity.md`)**: `` {el *=gato} `` renders `"el gato"` and `` {el +*=gato} `` renders `"los gatos"` — the *module* picks the form, so the article agrees. `ranting` still knows no non-English vocabulary; the word list lives in the fork's `inflect_article_custom`. Five things are non-obvious. (1) **`ranting_core::ph_ext::parse` runs two passes**: `parse_pass(s, PreWords::English)` with the closed vocabulary the grammar has always had, then `parse_pass(s, PreWords::Open)` **only if that fails**, returning the strict error on double failure. That ordering is what makes every existing template byte-identical, and it is not optional — an open pre-word slot competing at the same priority makes `` {w is} `` parse as `pre="w "`, `noun="is"`, which broke 15 English call sites when tried. (2) `PreWords` is threaded through `star_candidates`'s closure into `pre_one_rep`, deliberately *not* a thread-local: this parser is differentially fuzzed and must not have invisible mode. (3) **`PH_EXT` was not widened to match, and cannot be.** A single regex has one preference order, so it cannot express "prefer the English reading, fall back to the open one" — widening its alternation would accept the same language but disagree on captures, which is what the differential test checks. `assert_parity` therefore compares `PH_EXT` against `parse_pass(.., English)`, not against `parse`; `PH_EXT` remains the exact reference grammar for the English pass, and the open pass is pinned by `ph_ext::tests::open_pass_only_for_input_english_rejects`. (4) **`get_article_or_so`'s `ArticleKind::Other` arm now calls `inflect_article_custom_with_context`** instead of returning `None`. Both halves are required: with the grammar widened but `Other` still returning `None`, the native word renders as *inert literal text* and `` {el +*=gato} `` gives `"el gatos"` — a compile error traded for silently wrong output. English impls return `None` by default, which is what leaves the word as written. (5) **The noun needs a case marker.** The open pass runs only when the English pass *fails*, and `` {la casa} `` does not fail — it parses as `noun="la"`, `post=" casa"`, the ordinary noun + post-noun-verb reading. So `` {el gato} `` is unchanged and still errors with `E0425: cannot find value 'el'`; only `` {el *=gato} ``-shaped placeholders reach the open pass. That follows from the priority ordering and cannot be had alongside English byte-identity. That `E0425` **wording is permanent** — see the `check_ident_path` bullet below for why it was investigated and found unfixable, and what was fixed instead. (6) **The open pass allows `pre` exactly one repetition**, enforced in `parse_pass` rather than in the matcher — `pre` is a *repeated* group whose capture keeps only the last repetition, so `` {de the *=gato} `` otherwise matched as two reps (`de `, `the `), retained only `the `, and silently **dropped** `de` (rendering `"El gato"`). Restricting the open *matcher* to one word does not fix this; the repetition happens a level up in `star_candidates`. General lesson for this parser: a new alternative in a repeated group is not local to that alternative. Both falsifiers use the feature (`ranting_es` accepts `el`/`la`/`los`/`las`/`un`…, `ranting_i18n` accepts `der`/`die`/`das`/`den`/`dem`/`des`/`ein-`), so it is exercised by real forks and not only by a synthetic fixture. `heed!()`/`ask!()`/`#[derive(Heed)]` are **unaffected** — `ranting_derive/src/heed.rs` never references `ph_ext`. See `tests/ranting/native_article_keyword.rs`, `ranting_es/tests/spanish.rs::native_spanish_article_keywords`, `ranting_i18n/tests/german.rs::native_german_article_keywords`.
- **Regular pluralization, and the `plural_end` contract (ROADMAP.md Phase 7 item 10, 2026-08-14)**: until this landed there were *no* regular rules — `Ranting::inflect()` looked the noun up in `IRREGULAR_PLURALS` and otherwise appended `plural_end` (default `"s"`) verbatim, so `{+entity}` rendered `"entitys"` and `{+box}` rendered `"boxs"`. `src/language/plurals.rs` now has `regular_plural`/`compound_plural`, reached through the new public `ranting::inflect_noun_regular`, which is what the four derive-generated `inflect()` fallback sites in `ranting_derive/src/ranting_impl.rs::get_plurality_fns` call. Five things are non-obvious. (1) **Which path runs is decided by the `singular_end`/`plural_end` attributes, and that is the compatibility contract**: at their defaults the English orthographic rules apply, but a struct that *sets* either one has declared its own rule and still gets the literal strip-and-append — that is what stops a non-English impl using `plural_end` as an escape hatch from silently acquiring English spelling. They arrive as runtime `&str` (not resolved in the macro) because `= "$"` reads them from the struct's own fields. (2) The rules are **orthographic only**, a function of spelling alone, so they need no lexicon; `hero`/`piano`, Latin `-us` vs. `bus`, and `quiz`→`quizzes` (consonant doubling conditioned by stress, not letters) stay `data/irregular_plurals.txt` rows. The split defines what that table is *for*. (3) The `-f`/`-fe`→`-ves` stem lists look redundant with the table but aren't: `knife`/`wolf`/`shelf` are already rows, so those rules only ever fire for **compounds** the table's exact-match lookup misses (`bookshelf`→`bookshelves`). Their order matters — `shelf` before `self` before `elf`, each being a suffix of the previous. (4) **Singularization is deliberately unchanged** and still strips `plural_end`: every inverse rule has a counterexample class spelling can't separate from its positive class (`-ies`→`-y` fixes `cities` but breaks `movies`→`"movy"`, which the naive `-s` strip gets right; a `-ves`→`-f` suffix rule turns `olives` into `"olife"`), so `{-cities}` still renders `"citie"`. Pinned by `plurals::tests::singularization_is_deliberately_unchanged`; reopening it needs a lexicon, not a rule. (5) The rules run **wholly on a lowercased copy** and restore the caller's case afterwards, via the same `apply_case` the irregular path uses — except when the rule merely appends, where the name is left as written so interior capitals survive (`iPhone` → `iPhones`, which `apply_case` would lowercase). Matching on the lowercased form and slicing the *original* is not equivalent and was the first cut's bug: it rendered `CITY` as `"CITIes"` and panicked outright when lowercasing changed the byte length (`\u{212A}nife`, Kelvin sign → `knife`). `tests/ranting/property_based.rs::prop_inflect_no_panic` guards the panic class. (6) The spelling-only scope has a **concrete cost in `data/irregular_plurals.txt`**: the `-ch`-pronounced-/k/ words (`stomach`, `epoch`, `monarch`, …) needed rows, since the sibilant rule would otherwise say `"stomaches"` — before the rules landed they were right by accident, via bare append-`s`. `bus` is there for the same kind of reason on the singular side. Adding a rule to the engine means auditing what it now gets *wrong*. (7) **`ranting_gaps/src/english.rs` keeps its own copy of these rules on purpose** — it is the differential oracle the `regular-plural-rules`/`compound-head-plural` probes compare `ranting` against, so routing it through `ranting::inflect_noun_regular` would make them agree by construction and report zero findings forever. This is the `PH_EXT`-versus-`ph_ext` arrangement, not the hand-kept duplication warned about elsewhere in this file; both files carry the note. See `tests/ranting/regular_plurals.rs`.
- **Empty placeholders don't work** — `{}` is skipped; must name the variable.
- **Shared inflection code**: the placeholder grammar and pronoun logic live in `ranting_core::grammar` — both `ranting` and `ranting_derive` import from there directly (`use ranting_core::grammar as lang;` / `use ranting_core::grammar::SubjectPronoun;`, etc). There is no generated copy to keep in sync anymore; edit `ranting_core/src/grammar.rs` directly.
- **Auxiliary verb conjugation**: tense markers that need an auxiliary word (`>` future/`will`, `=` continuous/`is`-`are`, `<=` present-perfect/`have`-`has`, `%` past-continuous/`was`-`were`, `<%` past-perfect/`had`) get it from `src/language/auxiliary.rs`'s `AuxiliaryVerb`/`conjugate_auxiliary`, called from `handle_placeholder` in `src/lib.rs` — a layer not named elsewhere in this file's tense-marker documentation.
- **Verb table codegen**: `data/irregular_verbs.txt` is the single source of truth, and `ranting_core/build.rs` is the only build script that generates `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` from it (into `ranting_core`'s own `OUT_DIR`). Changing the data file triggers a rebuild via `cargo:rerun-if-changed`. Do not edit `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` by hand anywhere — they're generated, and both `ranting` and `ranting_derive` read `ranting_core::verb_conjugate::{IRREGULAR_PAST, IRREGULAR_PAST_PARTICIPLE}` rather than holding their own copies.
- **Runtime tense selection (`say_with!()`)**: without a `NarrationContext.tense` override, `say_with!()` reproduces `say!()`'s output exactly for the same placeholder (falls back to the placeholder's own marker).
- **Runtime viewpoint selection (`say_with!()`)**: `NarrationContext.narration_person` (`Person::First/Second/Third`) overrides which pronoun set and verb agreement render — but only for nouns declared first-person (`subject` is exactly `"I"` or `"we"`). Nouns declared `you`/`he`/`she`/`it`/`they`/etc. are never in scope, so a first-person narrator can be retold in third person while other characters in the same placeholder call keep their own declared pronouns unchanged (see `narration::resolve_viewpoint` in `src/narration.rs`). Third-person rendering always falls back to singular "they" — there's no gender data on a first-person-declared noun to render a gendered pronoun instead; a noun that wants gendered third-person output should declare that `subject` directly rather than relying on this override. Note also that `we` overridden to `Person::Second` renders "you" the same as `I` would — the original number can't be recovered from `Person::Second` alone, so this is a one-way rendering, not a round-trip.
- **Narration context threading (`register`/`dialect`, v1.1)**: `NarrationContext` also carries `register: Option<Register>` (`Formal`/`Neutral`/`Casual`) and `dialect: Option<&'static str>`, but the crate itself never interprets either — they're inert unless a `Ranting` impl reads them. Every verb/pronoun/article call site calls one of three new default trait methods, `inflect_verb_custom_with_context`/`inflect_pronoun_custom_with_context`/`inflect_article_custom_with_context` (joined in v1.3 by a fourth of the same shape, `inflect_adjective_custom_with_context` — see the adjective bullet below), which take `ctx: Option<&NarrationContext>` as a plain parameter (`say!()` passes `None`, `say_with!()` passes `Some(ctx)`) and default to delegating to the pre-existing non-context hook — so overriding only the `_with_context` hook is enough. `ctx` is never sourced from `self`/`subject`: that was deliberately rejected (see item 3's note on the trait-method mechanism) to keep an entity's own `subject` separate from story-wide settings.
- **`GrammaticalCase` on `inflect_article_custom`/`_with_context` (v1.3)**: a `case: GrammaticalCase` parameter, threaded from the placeholder's own `CaseKind` (the noun's case marker — `` {the =noun} `` is `Subjective`, `` {the @noun} `` is `Objective`, etc.; a bare `` {the noun} `` reports `GrammaticalCase::Name`, since English has nothing more specific to give). Added to close a gap a German-fork spike found (see `docs/architecture-review-2026-08-13.md`): without it, `inflect_article_custom` couldn't distinguish a placeholder acting as a subject from one acting as an object, so a case-declining language couldn't pick `der`/`den`/`dem` correctly — every call looked identical. `GrammaticalCase` mirrors `ranting_core::placeholder::CaseKind` exactly (via `impl From<placeholder::CaseKind> for GrammaticalCase`) rather than exposing `CaseKind` itself in the public trait, since `ranting_core` types aren't part of `ranting`'s public semver surface (see the "Architecture: Three Library Crates + Two Downstream Falsifier Crates" section above). See `tests/ranting/grammatical_case.rs` for a worked German nominative/accusative example — it also needs an `inflect_pronoun_custom` override that keeps returning the noun's own name, since `` {the =noun} ``/`` {the @noun} `` render the case-selected *pronoun* after the article, not the noun's name.
- **`NounClass` on the pronoun/article hooks (v1.3, ROADMAP.md Phase 6 item 2)**: an open-ended lexical-gender / noun-class label carried *by the entity*, threaded into `inflect_article_custom`/`_with_context` and `inflect_pronoun_custom`/`_with_context` as a `class` parameter (the verb hook is deliberately untouched — verb agreement is person/number, not class; the adjective hook received it too when Phase 6 item 5 landed — see the next bullet). Three things are non-obvious. (1) Unlike `GrammaticalCase`, `NounClass` is **not** mirrored from a `ranting_core` type: `CaseKind` exists there because the macro parses it out of placeholder syntax, but a noun class is never written in a placeholder, so there was nothing to mirror — `NounClass` is defined in `ranting` alone. It is a newtype over `&'static str`, not an `enum { Masculine, Feminine, Neuter }`, because Bantu has a dozen-plus classes and Danish has common/neuter; `ranting` never interprets the label, exactly like `NarrationContext::dialect`. (2) The `class` parameter is *redundant for a plain impl* — the hook has `self`, which already has `noun_class()` — but not for `Many`/`Maybe`/`Box`, where the call site reads the class off the *wrapper* while `self` inside the delegated-to hook is the *inner* value; that's why it's a parameter and why the wrappers override `noun_class()` (`Many` reports its single item's class only when `len() == 1`, `Maybe(None)` and a 0-or-2+ `Many` report `UNSET`). (3) `#[ranting(gender = "...")]` generates *no* `noun_class()` override at all when absent, so an unclassed impl is byte-identical to pre-v1.3 codegen; `gender = "$"` reads a `gender: ranting::NounClass` field (attribute name == field name, as for `name`/`subject`), which is how `Noun` itself carries one — set via `Noun::with_noun_class`, since `Noun`'s `Ranting` impl is derived and can't be hand-extended. See `tests/ranting/noun_class.rs` for the `der Hund`/`die Katze`/`das Haus` worked example and the `die Band`/`das Band` homograph pair that motivates carrying gender on the entity rather than in a `HashMap<&str, Gender>` keyed by the display string.
- **`inflect_adjective_custom` and the `!`-only adjective slot (v1.3, ROADMAP.md Phase 6 item 5)**: the first runtime adjective path in the crate — before it, degree (`!`/`!!`) was resolved wholly at compile time by `ranting_derive/src/language/adjective.rs` and `ranting` never saw an adjective. Four non-obvious points. (1) The hook is called only from the `PostSpec::Degree` arm of `handle_placeholder_impl`, i.e. **only for `{noun !adj}`/`{noun !!adj}`** — `PostSpec::Verb` (an unmarked post-noun word) is deliberately *not* routed to it, since handing a real verb to an adjective hook would break English. That makes `!` the only adjective channel there is, so a fork whose adjectives merely *agree* (French `noir`/`noire`/`noirs`) writes `!` for the positive degree and ignores the `degree` parameter; there is no `AdjectiveDegree::Positive` because there is no marker that would produce one. (2) `PostSpec::Degree` now carries **both** `base` (the adjective as written) and `word` (the compile-time English degree form), because the English form is not reversible back into the base — same bake-what-runtime-can't-re-derive shape as `say_with!()` baking the uninflected base verb into `PostSpec::Tense`. The hook gets `base`; `word` is only emitted on the `None` fallback path, which is what keeps `say!()`'s English output byte-identical. (3) `AdjectiveDegree` *is* mirrored from a `ranting_core` type (`placeholder::DegreeKind`, new in this change) via `From`, unlike `NounClass` — the degree marker is written in the placeholder, so there was something at the macro↔runtime seam to mirror. (4) Agreement is *form*, never *position*: French post-nominal vs. prenominal adjective placement is word order, which Phase 6 item 1 established stays in the caller's template. See `tests/ranting/adjective_agreement.rs` and `docs/EXTENSIBILITY.md` §2.5. Item 4's recommended count channel was **not** included when this item landed, but has since been added: ROADMAP.md Phase 6 item 14 gave this hook (and its `_with_context` twin) a `count: Option<PlaceholderCount>` parameter, between `as_plural` and `uc` — see the item 14 and item 4 bullets below.
- **`Ranting::capitalize` and the `OrthographyRole` sites (v1.3, ROADMAP.md Phase 6 item 6)**: every fallback path in `handle_placeholder_impl`/`get_article_or_so` that used to call `uc_1st_if` (or an inline uppercase-first-char block, for the tense and degree arms) now calls `capitalize`/`capitalize_with_context` instead, tagged with an `OrthographyRole` (`Article`/`Verb`/`Pronoun`/`Noun`/`Adjective`). Four things are non-obvious. (1) It returns `String`, not `Option<String>`, and so is deliberately *not* named `_custom`: it is the fallback, not a chance to decline one. Its default is exactly `uc_1st_if(word, uc)`, so English output is byte-identical; `inflect_*_custom` forms still apply `uc` themselves and never reach it, the pre-existing fallback-path-only contract. (2) `OrthographyRole` is **not** mirrored from a `ranting_core` type — same rule as `NounClass`, opposite of `GrammaticalCase`: a case marker is written in a placeholder so there is something at the macro↔runtime seam to mirror, but a call-site role is never written anywhere. (3) Four of the five roles get an uncapitalized word and a truthful `uc`; `OrthographyRole::Noun` is passed `uc: false`, because the name has already been through `inflect()` (which takes `uc` itself), and that is *not* equivalent to `uc_1st_if`: a derive-generated `name()` reads `uc == true` as "as written", not "force uppercase", so `#[ranting(name = "designer")]` renders lowercase even sentence-initially. Routing `uc` through the hook there would silently start capitalizing it — `tests/ranting/orthography.rs::lowercase_name_attribute_still_renders_lowercase` is the guard. The pre-noun possessive-substitution site (`` {`jane cat} `` → "Her cat") is `Noun` too, and likewise pre-capitalized. (4) The hook decides what is *done* with `uc`, never what `uc` *is*: sentence position and the `,`/`^` markers stay compile-time, and `apply_case` in `src/language/plurals.rs` (case *preservation* of an irregular plural's spelling, reached via the `self`-less `inflect_noun_irregular`) is not routed through it. `Many` delegates only at `len() == 1`, exactly like `noun_class()`.
- **`elide_article_custom` and the post-assembly splice (v1.3, ROADMAP.md Phase 6 item 7)**: the only hook in the crate that runs *after* the placeholder has been assembled rather than as a step within it. It receives the rendered `article`, the `separator`, and the rendered `following` text — whatever is actually adjacent to the article, i.e. any words the placeholder's own pre-text carried after it (`` {a set of $n chiens} `` gives `"set of 2 chiens"`), then the number, then the noun name or case-selected pronoun — and returns `Option<String>` replacing all three — French `le`+`homme` → `l'homme`, Italian `lo`/`il`/`l'`. Four non-obvious points. (1) It is a separate hook rather than a `following: &str` parameter on `inflect_article_custom` because at `get_article_or_so` time *the following text does not exist yet* — `nr` (the numeral push in `handle_placeholder_impl`) and the noun (the noun push in `handle_placeholder_impl`) are pushed afterwards, and the noun's form depends on `inflect()`/pronoun-case selection. The post-assembly shape also lets a fork drop the separator, which a parameter could not (the separator is emitted by a different call site). (2) The call site records the *byte span* of the last article pushed into `res` and splices after the noun; `get_article_or_so`'s signature is untouched, which is what makes English byte-identical by construction. The separator is collected from whitespace on **both** sides of that boundary — `space` is normally empty and the whitespace actually comes from `noun_space`, pushed later. (3) It takes **no `uc`** parameter, unlike the four `inflect_verb`/`pronoun`/`article`/`adjective` pairs and `capitalize` (item 8's numeral hook is the other `uc`-less one, for its own reason): the article arrives already capitalized (by `inflect_article_custom` or by `capitalize`), and `uc` has been reset to `false` by the splice point. (4) `de` + `le` → `du` was **not** reachable from this hook and still isn't — the preposition is template *literal* text outside the placeholder, and `` {de le chien} `` parses `de` as a pre-noun verb — but as of ROADMAP.md Phase 6 item 26 that gap has its own hook, `inflect_preposition_custom` (below), fed the literal word directly and called first at this same splice point; a hidden noun (`` {?the noun} ``) still renders nothing to elide against, so the splice sits inside the `case != Hidden` block and neither hook is called for it. See `tests/ranting/elision.rs` and `docs/EXTENSIBILITY.md` §2.7.
- **`inflect_preposition_custom` and the preceding-literal-word channel (v1.3, ROADMAP.md Phase 6 item 26)**: closes the gap the previous bullet's point (4) used to describe as permanent. `ranting_derive::parse_str_params` already read the template text immediately before a placeholder to compute `at_sentence_start` (collapsing it to a `bool`); item 26 widened `ranting_core::grammar::PH_START`'s `pre` capture to also match a single literal word plus its trailing whitespace, and instead of discarding that text, bakes it into `ranting_core::placeholder::PlaceholderSpec::preposition: Option<&'static str>`. `handle_placeholder_impl` renders that word itself now (the macro no longer emits it as inert literal format-string text), and calls `inflect_preposition_custom_with_context(preposition, article, case, class, as_plural, count, uc, ctx)` at the same post-assembly point `elide_article_custom` runs at, tried *first*: `Some` consumes both the rendered preposition and the article (reconstructing everything rendered after the article itself, since — unlike `elide_article_custom`'s `following` — this hook isn't handed a tail to rebuild), and `elide_article_custom` is skipped for that call; `None` leaves the preposition exactly as written and `elide_article_custom` still runs normally, so English is byte-identical either way. Only fires when the preposition is directly adjacent to the article (nothing rendered between them, e.g. no pre-noun verb) — the two-token signature has nowhere to put a mid-section. Widening `PH_START`'s alternation surfaced a latent quirk in this crate's `regex` version: `X?+` is not a possessive single-optional the way PCRE's is, empirically behaving as `(X?)+` (repeatable), which would have chained the new word branch across every preceding word (`"Vengo de "` instead of `"de "`) had the outer `pre` group been left as `?+` instead of changed to a plain `?`. `Many`/`Maybe`/`Box` delegate the pair with the same `len() == 1`/`own_count()` rule every other count-carrying `_custom` hook pair follows. See `tests/ranting/preposition_fusion.rs`, `docs/EXTENSIBILITY.md` §2.14, and `docs/superpowers/specs/2026-08-13-preposition-fusion.md`.
- **`inflect_numeral_custom` and where `#var` is now spelled (v1.3, ROADMAP.md Phase 6 item 8)**: the sixth `_custom` hook pair at the time (joined since by `inflect_preposition_custom`, item 26, as a seventh), covering both numeral channels — `#var` (spelled out) and `$var` (digits) — with `NumeralStyle::Words`/`Digits` telling them apart, plus `count: Option<i64>`, `GrammaticalCase`, `NounClass` and `as_plural`. Five things are non-obvious. (1) **`#var` moved from compile time to runtime.** The macro used to bake `ranting::rant_convert_numbers(n as i64)` into the `format!()` argument, i.e. a finished English word; it now bakes the *count* and `handle_placeholder_impl` calls the same speller as the hook's fallback. That is the whole reason a fork can replace the speller rather than post-process its output, and it is also why `handle_placeholder`/`_with_context` grew a `count: Option<i64>` parameter (a runtime value, so it could not go in the `Copy` `PlaceholderSpec`). `$var` was *not* moved: its argument need only be `Display`, so it is still rendered by the macro's `format!()` with the `:fmt` spec applied, and its count is recovered at runtime by `parse::<i64>()` on that string — `None` for a float, padding, or a non-numeric argument. Baking `as i64` for `$var` would fail to compile code that works today. (2) The number's **leading space moved out of the rendered string** into `placeholder::NumeralSpec::leading_space`, so the hook is handed the numeral alone and a replacement can't accidentally eat or duplicate the space; a `:fmt` width spec is *not* re-applied to a hook's return value. `NumeralSpec` is `None` both for a placeholder with no number and for a hidden one (`` {?$n noun} ``) — nothing renders, so the hook isn't called, same rule as `elide_article_custom`. (3) It closed item 8's own stated prerequisite instead of documenting around it: the `#var` arm of the `as_pl` match tests `count != Some(1)` now, not `nr.trim_start() != "one"`. Equivalent for English (`rant_convert_numbers` spells only 1 as `"one"`; -1 is `"negativeone"`), and it means agreement is decided *before* the hook runs, so a custom numeral can never flip it. `$var`'s arm is deliberately untouched — its `s != "1" && s.split('.').next() != Some("1")` also catches `"1.0"`, which a parsed `i64` would not. (4) It takes **no `uc`**, like `elide_article_custom`: the crate never capitalizes a numeral, a sentence-initial placeholder spends `uc` on the article/verb/noun. (5) The count here is *local to the numeral* and does **not** discharge item 4's owed count channel on the other eight hooks; `heed!()`/`ask!()`'s `{$name}` is input parsing and isn't routed here either. See `tests/ranting/numeral.rs` (Russian `два`/`две` off `NounClass`, Devanagari digits, and English byte-identity guards captured from the pre-change sources) and `docs/EXTENSIBILITY.md` §2.8.
- **The count channel, plus `case` on `Ranting::inflect` (v1.3, ROADMAP.md Phase 6 item 14)**: the owed signature break from item 4's design spike, done once. Added `count: Option<PlaceholderCount>` to `inflect_verb_custom`, `inflect_pronoun_custom`, `inflect_article_custom`, `elide_article_custom` and `inflect_adjective_custom` (and their five `_with_context` twins — ten methods in one commit, `6819ef02`), sourced from the placeholder's own `#var`/`$var` marker, `None` for a bare placeholder. `inflect_numeral_custom` was deliberately left alone — it already had a richer `count: Option<i64>` of its own (item 8), so a second, differently-typed count parameter there would have been redundant. Separately, `Ranting::inflect` gained a fourth parameter, `case: GrammaticalCase` — item 10's hole 2 (German dative/genitive) wanted it, and threading it through was free once `case` was already being computed for the article/pronoun hooks at the same call site; repairing `ranting_i18n` against this break found the `case` parameter does **not** by itself close hole 2, since `GrammaticalCase` still only carries English's five-marker inventory (see item 18/24's `GrammaticalCase` scoping bullet in §2.3.1 of `docs/EXTENSIBILITY.md`). `count` *is* usable today — `inflect_numeral_custom`'s German worked example (item 8, `tests/ranting/numeral.rs`) routes `два`/`две` off it. - **`Many` supplies its own length as the count (v1.3, ROADMAP.md Phase 6 item 15)**: `inflect_verb_custom`, `inflect_pronoun_custom`, `inflect_article_custom`, `elide_article_custom` and `inflect_adjective_custom` (and their five `_with_context` twins) take a `count: Option<PlaceholderCount>` parameter — joined since by `inflect_preposition_custom` (item 26), which follows the identical rule though it landed too late to be one of the original five this bullet was written about — sourced from the placeholder's own `#var`/`$var` marker and `None` for a bare placeholder (`` {noun} ``, `` {+noun} ``, `` {-noun} ``) — see `docs/superpowers/specs/2026-08-13-number-categories.md`. `Many<T>` (`src/collections.rs`) is the one wrapper that knows a count without any numeral in the placeholder at all: its own `Vec`'s length. When `Many` delegates one of those hook pairs to its single item (the pre-existing `len() == 1` rule those hooks already followed for `noun_class()`/`capitalize()`/`elide_article_custom`'s own doc notes), it now substitutes `count.or_else(|| self.own_count())` before forwarding — so a fork's hook sees `Some(PlaceholderCount { value: 1, .. })` in place of `None`, and an explicit placeholder numeral is left untouched (`Many` only fills the gap, never overrides). - **What `as_plural: bool` promises (v1.3, ROADMAP.md Phase 6 item 4)**: the `as_plural`/`to_plural` bool that appears in every one of the seven `_custom` hook *pairs* that carry number at all — fourteen methods, counting each hook and its `_with_context` twin; three pairs until Phase 6 item 5 added the adjective pair, item 7 the elision pair, item 8 the numeral pair and item 26 the preposition-fusion pair (an earlier version of this bullet said "six"/"eight", counts that went stale at items 7 and 26 respectively) — in `Ranting::is_plural()`/`inflect()`, and in the public `inflect_possessive`/`inflect_reflexive`/`inflect_noun_irregular` free functions promises exactly one thing — *render the plural **agreement** form* — resolved per placeholder occurrence at `src/lib.rs`'s `as_pl` match in `handle_placeholder_impl` from the `+`/`-`/`#var`/`$var` marker or `noun.is_plural()`. Neither changes anything for the other six pairs, and `$var`'s count is still recovered by parsing a rendered string there too.) The design spike is `docs/superpowers/specs/2026-08-13-number-categories.md`; its recommendation is to keep the bool authoritative for English and add a *count* parameter (never a category — CLDR stays out of the crate) alongside it. That count did **not** land with Phase 6 item 5, which was the spike's recommended landing site — the owed second hook-signature break sat open through items 5-8 and 26 — but it has since landed: Phase 6 item 14 (see the bullet immediately below) added `count: Option<PlaceholderCount>` to all five of the then-existing count-less pairs (verb, pronoun, article, elision, adjective) in one signature change, so as of item 14 every non-numeral pair carries both `as_plural` and a real count, and only `$var`'s own recovery (parsing a rendered string) remains string-sniffed. The trap this bullet used to close on — `src/lib.rs`'s `#var` arm comparing against the literal English word `"one"`, so a fork overriding `#var` rendering silently got plural agreement for a count of one — is **gone**: Phase 6 item 8 made that arm test the baked count (`count != Some(1)`) instead, and it is evaluated before the numeral hook runs, so a custom numeral cannot reach it.
- **`heed!()` capture syntax**: `{name}` captures one whitespace-delimited token; `{name...}` captures greedily up to the next literal or end of input; `{$name}` captures digits and parses them to `u64`. Two captures with no literal text between them is a compile-time error (ambiguous — there's no way to know where one capture ends and the next begins). Return type is positional, like `say!()`: bare `Option<T>` for 0/1 captures, `Option<(T1, T2, ...)>` for 2+.
- **Whitespace is `heed!()`/`ask!()`/`#[derive(Heed)]`'s only word boundary, permanently (v1.3, ROADMAP.md Phase 6 item 9)**: a *decided restriction*, not an unfinished edge — no tokenizer hook exists or will. It covers all three surfaces because all three go through the one compiler (`heed_derive::derive_heed` calls `compile_heed_template` too), even though the ROADMAP item's title names only two. The mechanism is `build_heed_pattern` in `ranting_derive/src/heed.rs`, which joins every pair of adjacent segments with a mandatory `\s+` (a punctuation-only literal is the sole exception, attaching to the preceding segment); `{name}` is `\S+`, `{$name}` is `\d+`, `{name...}` is `.+?`. Three consequences are worth being precise about. (1) It is **not** an ASCII/Latin restriction — the regex is script-agnostic, so `heed!("取る {item}", "取る 剣")` → `"剣"` and `heed!("เอา {item}", "เอา ดาบ")` → `"ดาบ"` work exactly like the English examples; what fails is a template whose segments abut, in any script. (2) The failure is an honest `None`, never a wrong capture — `heed!("{item}を取る", "剣を取る")` and `heed!("{a}的{b}", "我的剑")` both return `None` rather than letting regex backtracking invent a split, which is the same "don't silently guess" stance that makes two zero-gap captures a *compile* error. (3) The escape hatch is that an unspaced clause is exactly one `\S+` token, so `heed!("{clause}", "剣を取る")` hands the whole run back for the caller's own segmenter. The punctuation-only exemption is script-agnostic too (`` {item}、 取る `` matches `"剣、 取る"`) but is *per-segment*: `` {item}、取る `` is one alphanumeric-containing literal token, so it takes the `\s+` and returns `None`. Rejected: a pluggable tokenizer boundary in `compile_heed_template` — see DONE.md Phase 6 item 9 for why the compile-time/runtime split makes that a new registration mechanism nothing else in the crate has. Pinned by `tests/ranting/script_segmentation.rs`.
- **`ask!()` and `Answerable` (Phase 5, v1.2.1)**: `ask!(speaker, audience, template, input)` reuses `heed!()`'s template compiler (`ranting_derive/src/heed.rs::compile_heed_template`) to parse `input` against `template`, then forwards the captures to `audience.answer(&speaker, captures)` — the `Answerable` trait (`src/answerable.rs`). Unlike `heed!()`, captures are always plain `String`/tuples of `String` regardless of `{$name}` markers (no `u64` conversion) — `Answerable::Captures` is a fixed associated type, so parse what you need inside `answer()`. Returns `Option<String>`, `None` on no match, without calling `answer()` at all. Known limitation: `Captures` being per-type means one implementor supports exactly one capture arity everywhere it's used as an `ask!()` audience.
- **`say_with!()` and `#[derive_ranting]` are re-exported from `ranting`** (ROADMAP.md Phase 6 item 12, closing a gap item 10 found as hole 1): `ranting` re-exports `say`/`ack`/`nay`/`heed`/`Heed`/`ask`/`say_with`/`derive_ranting`/`boxed_ranting_trait`/`ref_ranting_trait` from `ranting_derive` — every public macro, now including these two. Before item 12, a downstream crate depending on `ranting` alone could never construct a `say_with!()` call, so it could never deliver a `NarrationContext` and every `_with_context` hook then defined was unreachable in practice (`say!()` always passes `None` regardless) — a set that has only grown since (now seven `_custom`/`_with_context` pairs plus `capitalize`/`capitalize_with_context`, eight `_with_context`-suffixed methods total, following items 5-8, 14 and 26). `tests/ranting/reexports.rs` pins the fix by writing only `use ranting::*;` (no `use ranting_derive::*;`, unlike every other file under `tests/ranting/`) and calling both macros directly; `ranting_i18n` (public-API-only by construction, see the "Architecture: Three Library Crates + Two Downstream Falsifier Crates" section above) exercises `say_with!()` the same way in `tests/holes.rs`'s `hole_1_*` test, which now asserts a `NarrationContext::dialect` value actually arrives instead of asserting it never does.
- **`is_first_person_subject_custom` (v1.3, ROADMAP.md Phase 6 item 16)**: `narration::resolve_viewpoint` (`src/narration.rs`) used to gate `say_with!()`'s `narration_person` viewpoint override on a hard-coded `ranting_core::grammar::is_first_person_subject` — `matches!(subject, "I" | "we")`, with no override. That was the one named residual gap in `docs/superpowers/specs/2026-08-13-pronoun-inventory.md` (open question 1): a fork whose first-person labels are `ich`/`wir` got a silent no-op, since `resolve_viewpoint` never recognized the noun as first-person and `narration_person` did nothing. `is_first_person_subject_custom(&self, subject: &str) -> bool` on `Ranting` closes it — defaults to exactly the old hard-coded check, so English output is byte-identical, and `resolve_viewpoint` now takes `noun: &R` and calls `noun.is_first_person_subject_custom(declared_subject)` instead of the free function directly. `Many`/`Maybe`/`Box` all delegate it (the same `len() == 1` rule as `noun_class()` for `Many`), so wrapping a fork's impl doesn't lose the override. See `tests/ranting/first_person_hook.rs` and `docs/EXTENSIBILITY.md` §2.10.
- **Sentence detection beyond Latin punctuation, and `capitalize`'s `sentence_start` parameter (v1.3, ROADMAP.md Phase 6 item 17)**: `ranting_core::grammar::PH_START` used to recognize a placeholder as sentence-initial only after an ASCII `.`/`?`/`!` followed by whitespace — silently missing Greek's question mark (U+037E, visually a semicolon but a distinct codepoint), Japanese/Chinese full-width terminators (`。`/`！`/`？`, which take no following space at all), Urdu's full stop (U+06D4), and Spanish's opening `¿`/`¡` (which mark sentence-initial from *before* the placeholder rather than after a prior sentence). `PH_START` now recognizes all of these, each with the shape its script actually needs: ASCII/Greek/Urdu terminators still require `\s+` after them; the CJK terminators need none; Spanish's opening marks take `\s*+` (optional). `ranting_core::grammar::SENTENCE_TRIGGER_CHARS` lists the same characters for `ranting_derive`'s `at_sentence_start` check (`ranting_derive/src/lib.rs`), which is its only reader. Note the two are **not** structurally coupled: `PH_START` is a `concat!` of string literals with the trigger characters hard-coded in its own character class, and a `concat!` cannot interpolate a `&[char]` const, so the lists are kept in step by hand. Changing one means changing the other — there is no mechanism preventing drift, only this note and the tests. Separately, this closed open question 2 of `docs/superpowers/specs/2026-08-13-word-order-feasibility.md`: `Ranting::capitalize`/`capitalize_with_context` (item 6) gained a `sentence_start: bool` parameter, baked at compile time into `ranting_core::placeholder::PlaceholderSpec` (unlike `uc`, which is not a `PlaceholderSpec` field at all — the macro passes it as a separate argument to `handle_placeholder`) — `uc` conflates "sentence-initial" with "forced uppercase by a `^`/`,` marker or an uppercase pre-text word", so `` {The 0} `` mid-sentence has `uc == true, sentence_start == false` and `` {,noun} `` right after a period has the reverse. `Many`/`Maybe`/`Box` (`src/collections.rs`) all thread the new parameter through their existing delegation rules unchanged. See `tests/ranting/sentence_detection.rs` (Greek/Japanese/Spanish, plus an ASCII regression guard), `tests/ranting/orthography.rs`'s `sentence_start`-divergence tests, and `docs/EXTENSIBILITY.md` §2.6.
- **Case marking and pronoun display now split apart, via fused `*=`/`*@`/`` *` ``/`*~`/`*%` markers (v1.3, ROADMAP.md Phase 6 item 19, found by item 10's hole 5)**: a case marker used to do two jobs at once — tell `inflect_article_custom` the noun's grammatical role, *and* switch the noun slot from name to pronoun. A fork whose `inflect_pronoun_custom` always returns the noun's own name (the typical shape, per `tests/ranting/grammatical_case.rs`'s `GermanNoun`) had no way to ask for "case-mark this, but still show the name" for a fork whose pronoun hook returns a *real* pronoun instead — `say!("Ich sehe {@0}.", hund)` would render "Ich sehe Hund." instead of "Ich sehe ihn." Closed by reusing `*` rather than adding a new marker character: `*` was already a case-marker-position character, previously synonymous with no marker at all (`CaseKind::Name`); fusing it with a real case marker (`*=`, `*@`, `` *` ``, `*~`, `*%`) case-marks the placeholder exactly like the bare marker (`inflect_article_custom`/`elide_article_custom` see the identical `GrammaticalCase`) but renders the name via `noun.inflect()` instead of calling `inflect_pronoun_custom`. Runtime: `PlaceholderSpec` gained one field, `display_as_name: bool`, `false` for every pre-existing placeholder, so `say!()`'s output is byte-identical by construction; `handle_placeholder_impl` checks it once before the `case`-dispatch match, and when set calls `noun.inflect(as_pl, uc, case.into())` with the *real* grammatical role rather than the always-`GrammaticalCase::Name` that `CaseKind::Name`/`Hidden` pass — a free side benefit any fork's own `inflect()` can use, and it narrows (without closing) `ranting_i18n`'s hole 2. Grammar: `ranting_core::grammar::PH_EXT`'s `case` capture tries the fused two-character form first (`` \*[`=@~%] ``), falling back to the single-character class; `ranting_core::ph_ext::case_one_rep` mirrors it by hand. `` *? `` and `**` are deliberately not accepted **as fused case markers** (`?` already means hidden; a second `*` has no defined meaning). They are not rejected outright: each parses as two ordinary single-character reps, so `` {*?who} `` and `` {**who} `` compile and render — only the fused reading is refused. `ranting_i18n` dropped its `Render`/`GermanNoun::as_pronoun` workaround entirely once this landed — hole 5 is struck from `ranting_i18n/README.md`. See `tests/ranting/case_display_split.rs`, `docs/EXTENSIBILITY.md` §2.11, and README.md's marker list.
- **The word-order boundary (v1.3, ROADMAP.md Phase 6 item 20)**: `ranting` inflects words within a template; the order of those words is the template's, and the template is the caller's — so a non-English application needs one template per language, and no inflection hook will ever change that. This is a permanent boundary, not a gap awaiting a future hook. See `docs/EXTENSIBILITY.md` §2.12 for the full reasoning, the named list of unreachable constructions, and the German attributive-adjective example that illustrates it sharpest.
- **`check_ident_path`, `path_from`'s span, and why `{el gato}`'s message is permanent (v1.3, ROADMAP.md Phase 7 item 8)**: a placeholder's noun is baked as a `syn::Ident`, and two separate things were wrong with that. (1) **`syn::Ident::new` panics on a non-identifier**, and `ph_ext`'s word matcher admits `-` and `'`, so `` say!("X {gato-negro}.") `` parsed fine and then surfaced as a bare `error: proc macro panicked` with the caret on the whole macro. `check_ident_path` now guards it and returns an `Err` through the existing `StrLitSlice::error` path, which underlines the offending word. The guard must use `syn::Ident::parse_any`, **not** `syn::parse_str::<syn::Ident>`: `Ident::new`'s rule is "a keyword *or* a legal variable name", and `` {self} ``/`` {=self do} `` are live syntax throughout `tests/ranting/male_female_and_object.rs` — the strict predicate broke five call sites. (2) **`path_from` now takes the template literal's span** instead of `Span::call_site()`, which moves rustc's own `E0425` caret from the whole `say!(...)` invocation onto the literal — and, the actual win, drops the `= note: this error originates in the macro \`say\`` line that otherwise tells the reader the real problem is somewhere they can't see. That is the *only* improvement available for `E0425`: the message is rustc's and cannot be intercepted or annotated by a proc macro, and the macro cannot decide to reject the template instead, because `` {el gato} `` and `` {person walk} `` are the same shape — one is a mistyped Spanish article, the other live English syntax, and which is which is name-resolution knowledge that arrives strictly after expansion. Narrowing the span to the individual word needs `proc_macro2::Literal::subspan`, which is nightly-only and returns `None` on stable (confirmed on 1.97.1) — that is also why `ph_ext`'s parse errors print the "At `<template>`" + squiggle fallback rather than a real underline. **Do not re-open this as a fixable diagnostic**; the full reasoning, both rendered messages, and the rejected alternatives are in `docs/superpowers/specs/2026-08-14-language-modularity.md`'s "The `{el 0}` diagnostic, as far as it goes" appendix. Note also that this repo has **no compile-fail harness** — no `trybuild` — so both diagnostics were verified by compiling a scratch crate against a path dependency, and the pinned tests (`ranting_derive`'s `non_identifier_nouns_are_rejected_rather_than_panicking` / `plausible_variable_names_still_pass`) exercise `check_ident_path` directly rather than the rendered output.
- **Doctests in proc-macro crate**: `ranting_derive/src/lib.rs` can't run proc-macro examples easily; test in `ranting/src/lib.rs` instead.
- **Integration tests only**: Unit tests are sparse by design; test via macros in `tests/ranting/`.

## When adding grammar rules

1. **For new verb conjugation tables**: Edit `data/irregular_verbs.txt` (one line per verb: `base|past|participle`). The build scripts will regenerate the Rust tables at build time.
2. **For runtime inflection logic** (e.g., `detect_tense` in `src/language/verb.rs`, or pronoun/article rules in `src/language/english.rs`): edit the relevant file under `src/language/`. Test with `cargo test --features debug` to see placeholder transforms.
3. **For compile-time inflection logic** (e.g., `handle_param` in the derive macro): Edit `ranting_derive/src/lib.rs`. Both crates' code changes are independent after codegen separation.
4. Add doctests or integration tests demonstrating the new inflection in `tests/ranting/`.
