## Architecture status (read before extending the codegen machinery)

ROADMAP.md **Phase 4 (v1.2.0)** is fully complete (all 8 items). Beyond item 1's `ranting_core`
extraction (see the Architecture section below for the resulting structure): dependencies were
modernized (syn 2, darling 0.20+, `proc-macro-error`/`lazy_static` dropped, editions unified on
2024); the macro↔runtime interface was retyped — the old `caps: [&str; 5]` array and `~TENSE~`
sentinel are gone, replaced by `ranting_core::placeholder`'s typed `PlaceholderSpec`/`CaseKind`/
`PostSpec` (see the Architecture section below); and the public-API cleanup landed, including
fixing the `inflect_possesive` typo to `inflect_possessive`. The project was also relicensed to
plain MIT (`LICENSE.txt`) as part of this phase. Don't reintroduce a build.rs copy-into-`OUT_DIR`
mechanism for new shared code — add it to `ranting_core` instead.

## Architecture: Three Crates

**`ranting`** (main lib): Exports `Ranting` trait, `Noun` struct, `say!()` macro.  
**`ranting_derive`** (proc-macro): Implements `say!()`, `ack!()`, `nay!()`, `ask!()` macros. `ranting_impl.rs`'s `ranting_q` is the derive macro's core codegen entrypoint (builds the generated `Ranting` impl from the parsed `#[ranting(...)]` attributes); `str_lit.rs` wraps `syn::LitStr` for span-preserving compile-error substrings.  
**`ranting_core`** (plain rlib, v1.2): Internal-only shared grammar engine both of the above depend on as an ordinary path dependency — the `serde`/`serde_derive` pattern, where a proc-macro crate and its companion runtime crate both depend on a shared library crate rather than one crate generating a copy of the other's source at build time. Nothing in `ranting_core` is part of `ranting`'s public semver surface, even where `ranting` re-exports an item from it.

**What moved into `ranting_core`** (previously three separate build.rs-copy-into-`OUT_DIR` mechanisms, now one crate with no codegen-copying at all):
- `ranting_core::grammar` — the placeholder grammar (`PH_START`, `PH_EXT`), `SubjectPronoun` (+ `is_subject`/`is_subjective_plural`/`is_first_person_subject`), and the still-unused `Article`/`DemonstrativePronoun` enums (kept as documented dead code — see ROADMAP.md Phase 4 item 1's implementation notes for why they weren't wired up or dropped). Formerly `src/language/english_shared.rs` (repo root), copied into `ranting_derive`'s `OUT_DIR` at build time and required to compile under two different `strum` major versions simultaneously (`ranting`'s 0.27 and `ranting_derive`'s 0.24) because it was included verbatim into both crates. That constraint is gone: `ranting_core` depends on a single `strum` version (0.27), and both `ranting` and `ranting_derive` get it transitively — `ranting_derive`'s own `Cargo.toml` no longer lists `strum`/`strum_macros` at all.
- `ranting_core::verb_conjugate` — `to_past`/`to_continuous`/`to_future`/`to_past_participle`, plus the generated `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` tables (from `data/irregular_verbs.txt`, via `ranting_core/build.rs` — now the *only* place that codegen runs; `ranting`'s own `detect_tense` in `src/language/verb.rs` reads `ranting_core::verb_conjugate::IRREGULAR_PAST` instead of generating its own copy, and `ranting_derive` reads the same module for compile-time `say!()` literal baking).

**Also in `ranting_core`, added by Phase 4 items 3 and 6** (new modules, not part of the three-mechanism extraction above — together over 1200 lines, the majority of `ranting_core`):
- `ranting_core::placeholder` — the typed `PlaceholderSpec`/`CaseKind`/`PostSpec`/`ArticleKind`/`TenseMarker` types that replaced the old `caps: [&str; 5]` array and `~TENSE~`/`~DEGREE~` string sentinels at the macro↔runtime seam (Phase 4 item 3). `ranting_derive`'s `handle_param` bakes a `PlaceholderSpec` struct literal at compile time; `ranting`'s `handle_placeholder`/`handle_placeholder_with_context` (the module is re-exported via `pub use ranting_core::placeholder;`) consume it at runtime.
- `ranting_core::ph_ext` — a hand-written recursive-descent parser (`ph_ext::parse`) for the placeholder-internals grammar, replacing what the `PH_EXT` regex used to match (Phase 4 item 6). `ranting_derive`'s `parse_str_params` calls `ph_ext::parse` directly now; `PH_EXT` (in `grammar.rs`) is kept only as an `#[allow(dead_code)]` differential-fuzz reference oracle for `ph_ext`'s own test suite, not used at compile/runtime anymore.

**What stayed put, and why**: `src/language/plurals.rs`'s `get_plural`/`get_singular`/`apply_case` used to be hand-duplicated in `ranting_derive/src/language/plurals.rs` too, but that copy was never called from anywhere in `ranting_derive` — noun pluralization happens at `Ranting::inflect()` runtime in `ranting`, never baked at compile time by the derive macro, so there was no call site to wire it into. Rather than carry permanently-dead code (and the `IRREGULAR_PLURALS`-table build.rs codegen that fed it) forever, the `ranting_derive` copy was deleted outright (2026-08-13, alongside fixing `ranting_derive`'s standalone `cargo clippy -D warnings` — see ROADMAP.md Phase 4 item 6's follow-up note). The single remaining copy in `src/language/plurals.rs` is live: `english::inflect_noun_irregular`, which backs `Ranting::inflect()`'s irregular-noun path, delegates to it directly, so `Noun::inflect()` (and derive-generated `inflect()` impls) look up `data/irregular_plurals.txt` and preserve the original word's case pattern (all-caps/title-case/lowercase) via `apply_case`. `ranting_derive/src/language/adjective.rs` (comparative/superlative degree tables) is a different case and stayed in `ranting_derive` — it's genuinely used there for compile-time `!`/`!!` degree-marker baking, and `ranting` has no runtime use for it, so it was never one of the three shared-copy mechanisms Phase 4 item 1 replaced. See `docs/architecture-review-2026-08-13.md` for the pre-extraction history of the plurals drift, and ROADMAP.md Phase 4 item 1's implementation notes for the full reasoning.

**Deleted**: both crates' build.rs copy-into-`OUT_DIR` steps for the code above, `ranting_derive/data/english_shared_source.rs`, `ranting_derive/data/verb_conjugate_source.rs`, and `ranting_derive/data/irregular_verbs.txt` (the packaged-build symlink fallbacks for the old copy mechanisms — `ranting_core` has its own `data/irregular_verbs.txt` → `../../data/irregular_verbs.txt` symlink now, for its own build.rs). `ranting_derive/Cargo.toml` no longer depends on `strum`/`strum_macros` at all — the dual-strum-version compilation constraint the "Key constraint" paragraph used to describe no longer exists, because the code that constraint applied to now compiles exactly once, in `ranting_core`.

**Macro flow**: Derive crate parses placeholders at compile-time, generates `format!()` calls. Runtime: `handle_placeholder()` applies final inflections via `Ranting` trait. `say_with!()` (v1.1) takes a `NarrationContext` as its first argument and calls `handle_placeholder_with_context()` instead — placeholders with tense markers (`<`,`=`,`>`,`<=`,`%`,`<%`) bake the *uninflected base verb* rather than a compile-time-conjugated form, so the marker can be overridden at runtime by `context.tense`. `say!()`'s codegen and output are untouched by this — it still bakes fully-conjugated literals and calls the original `handle_placeholder()`.

**`heed!()` input parsing** (v1.1): `heed!(template, input)` is the inverse direction of `say!()`'s placeholder syntax, but a deliberately smaller grammar — literal words plus `{name}`/`{name...}`/`{$name}` captures only, no article/verb/pronoun-case markers (see `docs/superpowers/specs/2026-08-12-input-parsing-feasibility.md` for why full grammatical inversion isn't attempted). `ranting_derive/src/heed.rs` compiles the template into an anchored regex at compile time; `ranting::HeedMatcher` (`src/heed.rs`) owns the actual `regex::Regex` (compiled once, cached via `OnceLock`) so generated code never references `regex::` types directly — this is why `ranting_derive`'s regex 1.6.0 and `ranting`'s regex 1.11 never need to match versions.

**`#[derive(Heed)]`** (v1.3, ROADMAP.md Phase 3 item 8's v2): struct-level sugar over `heed!()`, not a separate matching engine — `ranting_derive/src/heed_derive.rs::derive_heed` calls the same `heed::compile_heed_template` used by the `heed!()` macro, then generates `impl StructName { pub fn heed(input: &str) -> Option<Self> }`. `#[heed(template = "...")]` on the struct declares the template; every capture must have a same-named field and vice versa (a one-to-one mapping — a stale field or an unmapped capture is a compile error, not a silently-ignored gap), and each field's type is checked against its capture kind (`String` for `{name}`/`{name...}`, `u64` for `{$name}`). Only structs (named fields, or a unit struct for a zero-capture template) are supported — no enums. Field declaration order doesn't need to match template capture order; the derive maps by name.

## Non-obvious behaviors

- **Named arguments work** — `say!("{=x}", x)` (positional) and `say!("{=x}", x = val)` (named) both work today; see `tests/ranting/argument_edge_cases.rs`.
- **Empty placeholders don't work** — `{}` is skipped; must name the variable.
- **Shared inflection code**: the placeholder grammar and pronoun logic live in `ranting_core::grammar` — both `ranting` and `ranting_derive` import from there directly (`use ranting_core::grammar as lang;` / `use ranting_core::grammar::SubjectPronoun;`, etc). There is no generated copy to keep in sync anymore; edit `ranting_core/src/grammar.rs` directly.
- **Auxiliary verb conjugation**: tense markers that need an auxiliary word (`>` future/`will`, `=` continuous/`is`-`are`, `<=` present-perfect/`have`-`has`, `%` past-continuous/`was`-`were`, `<%` past-perfect/`had`) get it from `src/language/auxiliary.rs`'s `AuxiliaryVerb`/`conjugate_auxiliary`, called from `handle_placeholder` in `src/lib.rs` — a layer not named elsewhere in this file's tense-marker documentation.
- **Verb table codegen**: `data/irregular_verbs.txt` is the single source of truth, and `ranting_core/build.rs` is the only build script that generates `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` from it (into `ranting_core`'s own `OUT_DIR`). Changing the data file triggers a rebuild via `cargo:rerun-if-changed`. Do not edit `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` by hand anywhere — they're generated, and both `ranting` and `ranting_derive` read `ranting_core::verb_conjugate::{IRREGULAR_PAST, IRREGULAR_PAST_PARTICIPLE}` rather than holding their own copies.
- **Runtime tense selection (`say_with!()`)**: without a `NarrationContext.tense` override, `say_with!()` reproduces `say!()`'s output exactly for the same placeholder (falls back to the placeholder's own marker).
- **Runtime viewpoint selection (`say_with!()`)**: `NarrationContext.narration_person` (`Person::First/Second/Third`) overrides which pronoun set and verb agreement render — but only for nouns declared first-person (`subject` is exactly `"I"` or `"we"`). Nouns declared `you`/`he`/`she`/`it`/`they`/etc. are never in scope, so a first-person narrator can be retold in third person while other characters in the same placeholder call keep their own declared pronouns unchanged (see `narration::resolve_viewpoint` in `src/narration.rs`). Third-person rendering always falls back to singular "they" — there's no gender data on a first-person-declared noun to render a gendered pronoun instead; a noun that wants gendered third-person output should declare that `subject` directly rather than relying on this override. Note also that `we` overridden to `Person::Second` renders "you" the same as `I` would — the original number can't be recovered from `Person::Second` alone, so this is a one-way rendering, not a round-trip.
- **Narration context threading (`register`/`dialect`, v1.1)**: `NarrationContext` also carries `register: Option<Register>` (`Formal`/`Neutral`/`Casual`) and `dialect: Option<&'static str>`, but the crate itself never interprets either — they're inert unless a `Ranting` impl reads them. Every verb/pronoun/article call site calls one of three new default trait methods, `inflect_verb_custom_with_context`/`inflect_pronoun_custom_with_context`/`inflect_article_custom_with_context`, which take `ctx: Option<&NarrationContext>` as a plain parameter (`say!()` passes `None`, `say_with!()` passes `Some(ctx)`) and default to delegating to the pre-existing non-context hook — so overriding only the `_with_context` hook is enough. `ctx` is never sourced from `self`/`subject`: that was deliberately rejected (see item 3's note on the trait-method mechanism) to keep an entity's own `subject` separate from story-wide settings.
- **`GrammaticalCase` on `inflect_article_custom`/`_with_context` (v1.3)**: a `case: GrammaticalCase` parameter, threaded from the placeholder's own `CaseKind` (the noun's case marker — `` {the =noun} `` is `Subjective`, `` {the @noun} `` is `Objective`, etc.; a bare `` {the noun} `` reports `GrammaticalCase::Name`, since English has nothing more specific to give). Added to close a gap a German-fork spike found (see `docs/architecture-review-2026-08-13.md`): without it, `inflect_article_custom` couldn't distinguish a placeholder acting as a subject from one acting as an object, so a case-declining language couldn't pick `der`/`den`/`dem` correctly — every call looked identical. `GrammaticalCase` mirrors `ranting_core::placeholder::CaseKind` exactly (via `impl From<placeholder::CaseKind> for GrammaticalCase`) rather than exposing `CaseKind` itself in the public trait, since `ranting_core` types aren't part of `ranting`'s public semver surface (see the "Three Crates" section above). See `tests/ranting/grammatical_case.rs` for a worked German nominative/accusative example — it also needs an `inflect_pronoun_custom` override that keeps returning the noun's own name, since `` {the =noun} ``/`` {the @noun} `` render the case-selected *pronoun* after the article, not the noun's name.
- **`NounClass` on the pronoun/article hooks (v1.3, ROADMAP.md Phase 6 item 2)**: an open-ended lexical-gender / noun-class label carried *by the entity*, threaded into `inflect_article_custom`/`_with_context` and `inflect_pronoun_custom`/`_with_context` as a `class` parameter (the verb hook is deliberately untouched — verb agreement is person/number, not class; the adjective hook gets it when Phase 6 item 5 lands). Three things are non-obvious. (1) Unlike `GrammaticalCase`, `NounClass` is **not** mirrored from a `ranting_core` type: `CaseKind` exists there because the macro parses it out of placeholder syntax, but a noun class is never written in a placeholder, so there was nothing to mirror — `NounClass` is defined in `ranting` alone. It is a newtype over `&'static str`, not an `enum { Masculine, Feminine, Neuter }`, because Bantu has a dozen-plus classes and Danish has common/neuter; `ranting` never interprets the label, exactly like `NarrationContext::dialect`. (2) The `class` parameter is *redundant for a plain impl* — the hook has `self`, which already has `noun_class()` — but not for `Many`/`Maybe`/`Box`, where the call site reads the class off the *wrapper* while `self` inside the delegated-to hook is the *inner* value; that's why it's a parameter and why the wrappers override `noun_class()` (`Many` reports its single item's class only when `len() == 1`, `Maybe(None)` and a 0-or-2+ `Many` report `UNSET`). (3) `#[ranting(gender = "...")]` generates *no* `noun_class()` override at all when absent, so an unclassed impl is byte-identical to pre-v1.3 codegen; `gender = "$"` reads a `gender: ranting::NounClass` field (attribute name == field name, as for `name`/`subject`), which is how `Noun` itself carries one — set via `Noun::with_noun_class`, since `Noun`'s `Ranting` impl is derived and can't be hand-extended. See `tests/ranting/noun_class.rs` for the `der Hund`/`die Katze`/`das Haus` worked example and the `die Band`/`das Band` homograph pair that motivates carrying gender on the entity rather than in a `HashMap<&str, Gender>` keyed by the display string.
- **What `as_plural: bool` promises (v1.3, ROADMAP.md Phase 6 item 4)**: the `as_plural`/`to_plural` bool that appears in all six `_custom` hooks, in `Ranting::is_plural()`/`inflect()`, and in the public `inflect_possessive`/`inflect_reflexive`/`inflect_noun_irregular` free functions promises exactly one thing — *render the plural **agreement** form* — resolved per placeholder occurrence at `src/lib.rs:371-381` from the `+`/`-`/`#var`/`$var` marker or `noun.is_plural()`. It does **not** promise the referent count is greater than one: `is_subjective_plural("they")` is `true` (singular *they* — plural agreement, singular reference), an empty `Many` is plural ("there **are** no items"), and `inflect_reflexive` special-cases the same bool to pick `yourself`/`yourselves` because "you" is number-underspecified everywhere else. It also does not let a fork recover the count: `nr` is already a formatted `String` by the time `handle_placeholder_impl` runs (and `#var` is already English *words*), the bool is recovered from it by string-sniffing, and that string is never passed to a hook — so Arabic dual, Slavic paucal and CLDR `zero/one/two/few/many/other` are unreachable today, with no side-table workaround. The design spike is `docs/superpowers/specs/2026-08-13-number-categories.md`; its recommendation is to keep the bool authoritative for English and add a *count* parameter (never a category — CLDR stays out of the crate) alongside it when Phase 6 item 5 changes the hook signatures. Related trap: `src/lib.rs:376` compares against the literal English word `"one"`, so a fork that overrides `#var` numeral rendering (Phase 6 item 8) silently gets plural agreement for a count of one.
- **`heed!()` capture syntax**: `{name}` captures one whitespace-delimited token; `{name...}` captures greedily up to the next literal or end of input; `{$name}` captures digits and parses them to `u64`. Two captures with no literal text between them is a compile-time error (ambiguous — there's no way to know where one capture ends and the next begins). Return type is positional, like `say!()`: bare `Option<T>` for 0/1 captures, `Option<(T1, T2, ...)>` for 2+.
- **`ask!()` and `Answerable` (Phase 5, v1.2.1)**: `ask!(speaker, audience, template, input)` reuses `heed!()`'s template compiler (`ranting_derive/src/heed.rs::compile_heed_template`) to parse `input` against `template`, then forwards the captures to `audience.answer(&speaker, captures)` — the `Answerable` trait (`src/answerable.rs`). Unlike `heed!()`, captures are always plain `String`/tuples of `String` regardless of `{$name}` markers (no `u64` conversion) — `Answerable::Captures` is a fixed associated type, so parse what you need inside `answer()`. Returns `Option<String>`, `None` on no match, without calling `answer()` at all. Known limitation: `Captures` being per-type means one implementor supports exactly one capture arity everywhere it's used as an `ask!()` audience.
- **Doctests in proc-macro crate**: `ranting_derive/src/lib.rs` can't run proc-macro examples easily; test in `ranting/src/lib.rs` instead.
- **Integration tests only**: Unit tests are sparse by design; test via macros in `tests/ranting/`.

## When adding grammar rules

1. **For new verb conjugation tables**: Edit `data/irregular_verbs.txt` (one line per verb: `base|past|participle`). The build scripts will regenerate the Rust tables at build time.
2. **For runtime inflection logic** (e.g., `detect_tense` in `src/language/verb.rs`, or pronoun/article rules in `src/language/english.rs`): edit the relevant file under `src/language/`. Test with `cargo test --features debug` to see placeholder transforms.
3. **For compile-time inflection logic** (e.g., `handle_param` in the derive macro): Edit `ranting_derive/src/lib.rs`. Both crates' code changes are independent after codegen separation.
4. Add doctests or integration tests demonstrating the new inflection in `tests/ranting/`.
