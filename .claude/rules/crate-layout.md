# Crate layout, shared code, and codegen

Read before adding a crate, moving code between crates, adding a build script, or "deduplicating"
anything.

## Architecture: three library crates + four downstream falsifier crates

The three crates below are the library. `ranting_i18n/` (crate name `ranting-i18n`, v1.3,
ROADMAP.md Phase 6 item 10), `ranting_es/` (crate name `ranting-es`, Phase 6 item 23),
`ranting_ar/` (crate name `ranting-ar`, Phase 7 item 5) and `ranting_ja/` (crate name
`ranting-ja`, Phase 7 item 6) are four more directories but *not* part of it: each is a downstream consumer that depends on `ranting`
alone, exactly as an ecosystem fork would, and exists to falsify the claim that the public API
gives a non-English implementation enough signal. Nothing in
`ranting`/`ranting_core`/`ranting_derive` depends on any of them, and **none may ever gain a
`ranting_core` or `ranting_derive` dependency — the moment one needs it, that is the finding.**

The falsifiers were chosen to exercise different, complementary gaps rather than duplicate
each other. `ranting_i18n` implements German and found that German attributive adjectives are
prenominal (`der kleine Hund`) while `ranting`'s `!`/`!!` degree slot is post-noun only, so German
structurally *cannot* reach `inflect_adjective_custom` in a grammatically correct sentence — only
demonstrate the agreement mechanism in isolation. `ranting_es` implements Spanish specifically
*because* Spanish attributive adjectives are post-nominal (`el gato negro`, `la casa negra`),
exactly where the `!` slot renders, so it exercises `inflect_adjective_custom` with genuinely
correct output rather than a position mismatch. `ranting_ar` implements Arabic and is the first
non-Indo-European one: it exists for a **third morphological number** (the dual, which forced
Phase 7 item 11's `count` onto `Ranting::inflect`) and to be `elide_article_custom`'s first real
user — the Phase 7 item 1 audit found that hook overridden by neither of the other two, since
German's and Spanish's real fusions are all preposition-side. It deliberately does **not**
implement `inflect_adjective_custom`: Arabic adjectives are post-nominal like Spanish's, so a
second working example would add no falsification. `ranting_ja` is the first fork whose decisive
finding is a **confirmation** rather than a gap — it is `NarrationContext::register`'s only real
consumer, inert since Phase 3 — plus one defect (the numeral-noun separator, Phase 7 item 12).
Only three of the eight hook pairs are live in it (verb, numeral, and the numeral elision it caused), and its README records that as a *finding* (the
surface degrades cleanly for a low-inflection language) rather than as holes.

Each crate's `README.md` is the authoritative, numbered list of what its language cannot reach through the public API, each pinned by a
`hole_N_*` test in its own `tests/holes.rs` that asserts what the crate *actually* renders.

`ranting_gaps/` (crate name `ranting-gaps`, binary `ranting-gaps`, ROADMAP.md Phase 7 item 9) is
a fifth non-library sibling and is **not** a falsifier — read its dependency list before treating
it as precedent. It is a development tool that reads arbitrary English text and reports what
`ranting` cannot inflect, ranked by corpus frequency, into a generated `failures/` tree. Because
its job is to inspect `ranting` from outside rather than to prove the public API sufficient, it
depends on `ranting_core` as well as `ranting` — deliberately, using `ranting_core::ph_ext::parse`
as the authoritative oracle for the closed pre-noun vocabulary rather than restating that word
list. That dependency does **not** relax the falsifier contract on
`ranting_i18n`/`ranting_es`/`ranting_ar`/`ranting_ja`, which remains absolute. `failures/` at the
repo root is its committed output, regenerated by rerunning the tool — never hand-edited.

`ranting_es_gaps/` (crate name `ranting-es-gaps`, binary `ranting-es-gaps`) is a sixth non-library
sibling, **also not a falsifier**, one level down from `ranting_gaps`: it inspects `ranting_es`
from outside instead of inspecting `ranting`. It depends on both `ranting` (for the trait/type
surface its probes call directly — `Ranting`, `GrammaticalCase`, `NounClass`, ...) and `ranting_es`
(the system under test), which is not a precedent for `ranting_es`'s own `ranting`-alone contract —
that contract lives in `ranting_es/Cargo.toml` alone and is unaffected by who else depends on it.
Unlike `ranting_gaps`, it does **not** discover new-word inflection bugs against an open
vocabulary: `ranting_es`'s lexicon is a closed set (4 nouns, 4 verbs, 3 adjectives, numerals
`0..=12`, every gender/conjugation hand-listed rather than suffix-generated), so there is no
general rule to test brand-new words against. Instead it enumerates every comparison the closed
lexicon can produce up front and uses a corpus only to grade each one's confidence — an
**enumerate-then-attest** model, not `ranting_gaps`'s **nominate-then-filter** one. See its own
README for the full rationale and what it deliberately cannot do.

**`ranting`** (main lib): Exports `Ranting` trait, `Noun` struct, `say!()` macro.
**`ranting_derive`** (proc-macro): Implements `say!()`, `ack!()`, `nay!()`, `ask!()` macros.
`ranting_impl.rs`'s `ranting_q` is the derive macro's core codegen entrypoint; `str_lit.rs` wraps
`syn::LitStr` for span-preserving compile-error substrings.
**`ranting_core`** (plain rlib, `0.1.0`): Internal-only shared grammar engine both of the above depend
on as an ordinary path dependency — the `serde`/`serde_derive` pattern. Nothing in `ranting_core`
is part of `ranting`'s public semver surface, even where `ranting` re-exports an item from it.

## Deliberate duplication — do not "fix" these

- **`ranting_gaps/src/english.rs` keeps its own copy of the regular plural rules.** It is the
  differential oracle the `regular-plural-rules`/`compound-head-plural` probes compare `ranting`
  against, so routing it through `ranting::inflect_noun_regular` would make them agree by
  construction and report zero findings forever. Both files carry the note.
- **`PH_EXT` (regex) vs. `ph_ext` (parser)** — same arrangement, see `placeholder-grammar.md`.
- **`PH_START`'s hard-coded trigger characters vs. `SENTENCE_TRIGGER_CHARS`** — kept in step *by
  hand*; a `concat!` cannot interpolate a `&[char]` const. There is no mechanism preventing drift,
  only this note and the tests. See `placeholder-grammar.md`.

## What lives in `ranting_core`

- `ranting_core::grammar` — the placeholder grammar (`PH_START`, `PH_EXT`), `SubjectPronoun`
  (+ `is_subject`/`is_subjective_plural`/`is_first_person_subject`), and the still-unused
  `Article`/`DemonstrativePronoun` enums (documented dead code — see DONE.md Phase 4 item 1 for
  why they weren't wired up or dropped). Edit `ranting_core/src/grammar.rs` directly; **there is no
  generated copy to keep in sync anymore.** Don't reintroduce a build.rs copy-into-`OUT_DIR`
  mechanism for new shared code — add it to `ranting_core` instead.
- `ranting_core::verb_conjugate` — `to_past`/`to_continuous`/`to_future`/`to_past_participle`,
  plus the generated `IRREGULAR_PAST`/`IRREGULAR_PAST_PARTICIPLE` tables.
- `ranting_core::placeholder` — the typed `PlaceholderSpec`/`CaseKind`/`PostSpec`/`ArticleKind`/
  `TenseMarker` types at the macro↔runtime seam (Phase 4 item 3). `ranting_derive`'s `handle_param`
  bakes a `PlaceholderSpec` struct literal at compile time; `ranting`'s
  `handle_placeholder`/`handle_placeholder_with_context` consume it at runtime.
- `ranting_core::ph_ext` — hand-written recursive-descent parser for the placeholder internals
  (Phase 4 item 6), replacing what `PH_EXT` used to match.

## What stayed put, and why

`src/language/plurals.rs`'s `get_plural`/`get_singular`/`apply_case`/`regular_plural`/
`compound_plural` used to be hand-duplicated in `ranting_derive/src/language/plurals.rs`, but that
copy was never called from anywhere — noun pluralization happens at `Ranting::inflect()` runtime in
`ranting`, never baked at compile time — so the `ranting_derive` copy was deleted outright
(2026-08-13). `ranting_derive/src/language/adjective.rs` (comparative/superlative degree tables) is
a different case and stayed in `ranting_derive` — it is genuinely used there for compile-time
`!`/`!!` degree-marker baking, and `ranting` has no runtime use for it.

## Build scripts — three, each generating a different table

| Script | Source of truth | Generates into |
|---|---|---|
| `ranting_core/build.rs` | `data/irregular_verbs.txt` | `IRREGULAR_PAST`, `IRREGULAR_PAST_PARTICIPLE` |
| `build.rs` (root) | `data/irregular_plurals.txt` | `ranting`'s irregular-plural table |
| `ranting_derive/build.rs` | `data/irregular_adjectives.txt` | irregular-adjective table |

Do not edit a generated table by hand. Changing a data file triggers a rebuild via
`cargo:rerun-if-changed`. Both `ranting` and `ranting_derive` read
`ranting_core::verb_conjugate::{IRREGULAR_PAST, IRREGULAR_PAST_PARTICIPLE}` rather than holding
their own copies.

## Macro flow

Derive crate parses placeholders at compile time, generates `format!()` calls. Runtime:
`handle_placeholder()` applies final inflections via the `Ranting` trait. `say_with!()` (v1.1) takes
a `NarrationContext` as its first argument and calls `handle_placeholder_with_context()` instead —
placeholders with tense markers bake the *uninflected base verb* rather than a compile-time
conjugated form, so the marker can be overridden at runtime by `context.tense`. `say!()`'s codegen
and output are untouched by this.
